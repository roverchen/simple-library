## 一、客製化需求清單 v2.0 中「不合理或需要修正」的地方

### 1. 用語不清、概念混淆（容易造成實作走偏）

- **「財產編號（目前是出版社分類）是每一本書的唯一號碼」**（4.1）：
  財產編號應為園所內部購買／資產編號（如 `A000125`），不是出版社分類；同段又把 ISBN（如 `9789577620981`）當財產編號用，兩種編號混用。
- **「欄位分離：必須有獨立『財產編號（Barcode）』欄位（唯一值、掃碼用）」**（4.5 系統設計總結）：
  Barcode（條碼）與財產編號是兩回事。原系統 schema 其實已有 `books.barcode`（條碼／掃碼主鍵）＋ `books.asset_id`（財產編號）兩欄，需求文應改寫為「條碼」與「索書號」分層。
- **2.1 內文有亂碼**：「…都固定 武夷艦第一個學生的名子，系統都是設定a01。」需校正；「以每學年為單位…（例如 a01 即為閱讀紀錄僅每學年有效）」語意不明。
- **1.2 / 1.5**：「借閱主體」未加條號；1.5 標題下順序混用「已歸還歷史紀錄」與「館藏查詢供老師調閱」，歸權描述不清。

### 2. 明顯自相矛盾 / 邏輯不通

- **期初借閱（一班 90 本）整批掃入系統…週五班級借閱時，老師自行登記** vs **借閱期限：一學期（2/1～7月底、8/1～1月底）** vs 情境「15 個孩童的週五借還書」——三個時間地點概念互相撞車。
- **「借閱紀錄僅維持每學年有效」**（2.1）vs **「上個月借沒還 / 2026 年借還紀錄明細」的爭議調查**（1.5）——紀錄只留每學年會影響跨年／永久保存的爭議調查，與「資料庫不會持續膨脹」的目標也撕裂。
- **5.1「還書不需掃老師條碼，只需掃『還書條碼』後掃『書籍財產編號』完成還書」**——「還書條碼」從未定義（應是功能指令條碼的「還書模式」？），術語不清。

### 3. 明顯不合理或可商榷的地方

- **3.2 交付要求**：要「封裝為 .exe（Electron）或自帶微型伺服器，嚴禁 file:// 開啟」。原系統**本來就是**「自帶微型伺服器（`localhost`）」，且 README／修訂紀錄早已警告勿用 `file://`——此項約束其實已滿足，若再要求「二選一並重交付」，建議只保留微型伺服器方案。
- **3.1 備份設計**：每日自動備份 + 保留 10 天循環覆蓋可行，但「三份檔案（已借出清單／使用者清單／圖書清單）匯入還原」與原系統**既有的完整 JSON 備份**是兩套機制，建議以完整備份為基礎改進。
- **5.1**：「刷老師條碼後，仍要『先選班級，再選成員』指定學生」——只換來源（條碼槍），流程仍靠選單，未真正達成「消滅滑鼠操作」。
- **4.5 索書號**：「書名第一個字取注音」對多音字、非注音開頭（如 `B`、`D` 拉丁字母）或空白字元，未定義例外規則。

### 4. 規格本身不完整

- 7.2 報表欄位清單缺少借閱人／借閱次數等常用維度；6.2 出版社模糊搜尋（如「上誼」）的統計邊界需定義；1.3 的「2/1～7月底、8/1～1月底」日期格式不完整。

## 二、原系統目前「需要修改的地方」（對應需求清單）

### 需求 → 原系統現況 → 需要修改的地方

| 需求區塊 | 原系統現況 | 需要修改的地方 |
|---|---|---|
| **1.權限分級／多帳號** | 已知限制：單一共用密碼、無多老師帳號／角色／稽核 | `schema.sql` 新增 `users` 表（系統管理員／系統 Root／老師／學生 + 角色）；`server.py` 改多帳號登入、Session 綁定帳號、密碼重置；`index.html` 登入／授權 UI |
| **1.2–1.4 借閱規則／期限／上限／續借／逾期** | 完全沒有：schema 無到期日、無借閱上限、無續借、無逾期判斷；`loan_logs` 只有 `occurred_at` | `schema.sql`：`books` 加借閱／到期資訊或 `loan_logs` 加 `due_at`；`server.py`：`api_loan` 增加期限檢核、數量上限、續借；新增「逾期未還清單」報表 |
| **2.學籍批次處理** | 班級／成員只能手動新增 | 新增 Excel／CSV 批次匯入 API（欄位對應 mapping 介面）；成員加入「學號／員工編號」；以學年為週期 |
| **3.安全性／備份／密碼** | 已有：SQLite + JSON 完整備份／還原、PBKDF2、12h session、localhost 限制、`file://` 警告；**缺**：每日自動備份、雲端備份、10 天循環覆蓋、還原到新電腦、密碼自救、雙軌制 | `server.py` 新增定時備份、保留週期、還原機制；新增密碼重置（安全提問／雙帳號） |
| **4.圖書館藏與財產管理** | `books` status 只有「在館／借出／報廢」；無「狀態備註」、無索書號欄位；報廢／復原已實作 | `schema.sql`：`status` CHECK 擴充為「在館／借出／遺失／修繕中／爭議中／報廢」；新增 `remarks`（瑕疵與缺件）；`call_no`（索書號）欄位＋自動產生；批次匯入圖書（財產編號） |
| **4.4 預約功能** | 完全沒有 | 新增預約狀態／排隊機制（書狀「借出」時排隊） |
| **4.5 索書號** | 無索書號欄位 | 新增索書號產生邏輯（主分類色＋次分類＝書名首字注音） |
| **5.加快借還書速度** | 借還流程需「先選班級→選成員→再掃書」；有槍輸入、QR 掃描、去重、防呆 | 新增幼兒／老師「借閱條碼」與批次列印名冊；新增「功能指令條碼」（啟動借書／還書／清除重來）；改流程為「刷幼兒條碼 → 刷書條碼」；還書模式指令碼＋批次還書（還書箱） |
| **6.館藏查詢系統（F06）** | 原無 F06：教師端沒有館藏查詢頁（管理端有書籍表） | 新增 API（查詢／ISBN／書名／複本彙整／位置／出版社統計）＋教師端查詢介面 |
| **7.報表／列印** | 已有：借閱紀錄分頁、CSV（UTF-8 BOM）、QR 標籤列印、完整備份 | 新增 xlsx/pdf 匯出；新增「逾期未還清單」；新增財產清冊／報廢清冊／借出清單；**個人閱讀歷程統計**需以「學號／員工編號」統計 → `loan_logs` 與 `members` 需建構關聯 |

### 原系統的「已知限制」其實正是 v2 需求要補的

- 單一共用密碼 → 1.1、3.3
- 相機需安全內容／`file://` → 3.2
- 借閱紀錄無法按日期篩選 → 1.5、2、7（個人閱讀歷程統計）
- 單一伺服器、無內建備援 → 3.1、3.2
- 手機版功能較少 → 5.1 的「條碼名冊列印」等

## 三、總結：最需要關注的三個問題

1. **矛盾與不完整是最大痛點**：財產編號≠出版社分類、Barcode≠財產編號、紀錄只留每學年卻要查「上個月沒還」、期初批次借閱 vs 週五還書、還書條碼未定義——建議先請園方校對修正，再交給廠商開發。
2. **原系統必須動的模組**（依重要性排序）：
   - `schema.sql` + `server.py`：`status` 擴充（遺失／修繕中／爭議中）、索書號欄位、借閱期限／續借／逾期、會員條碼、批次匯入、個人統計所需的成員-ID關聯；
   - `server.py` + 新 API：`F06` 館藏查詢、逾期／個人統計報表、密碼／帳號、每日備份與還原；
   - `index.html` / `mobile.html`：全靠條碼槍的借還流程、指令條碼模式、預約、條碼名冊列印、館藏查詢頁。
3. **可不必大改的部分**：SQLite 後端、`file://` 禁令、PBKDF2、JSON 備份、報廢層級、槍輸入與 QR 掃描、CSV UTF-8 BOM、列印隔離等——v2 多數要求是「照著已有設計補缺」，不必推翻重來。
